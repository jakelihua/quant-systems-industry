# 系统实验与运行手册

## 市场数据和数据血缘

数据拆为可追溯的入口批次、带版本的规范表和研究快照。每批记录源端、UTC 时间、交易日、品种、序号、原始消息 ID、schema 版本和校验值。品种日历、结算币种与市场阶段放在参考表里。原始错误记录进入单独隔离区。重放输入固定时，同一版本输出应一致，且失败有可定位的错误。

- **可知时点实验。** 财务期末值 100 于 4 月 10 日发布，4 月 15 日下修为 80。朴素历史查询在 4 月 9/11/16 日都返回 80，按可知时间查询依次得到缺失、100、80。用 source event time 做 as-of 仍可能漏掉供应商延迟与系统接收时间。使用 `available_at <= decision_cutoff` 查可用版本。[SQL](../lab/pit.sql)
- **盘口恢复实验。** 盘口从序号 10 开始，11 更新，重复 11 忽略。13 暴露缺口，14 到来时仍暂停使用，15 的完整快照恢复输出。单流实验以整数档与连续会话为域，真实接口还要考虑多通道序号、增量缓冲、交易阶段、上游重置和市场规则。[实现](../lab/data_plane.py) · [L2 规格入口](https://www.sseinfo.com/services/assortment/historical/)

## 订单链路和账本

行情 → 组合目标 → 母/子单 → 前置校验 → 发送 → 回执/成交 → 仓位与现金 → 外部对账。组合目标版本、订单 ID、外部成交 ID 和回报序号分别保存。网络超时属于未知结果，要询问外部状态或用相同幂等键恢复，随意更换请求 ID 可能生成第二笔订单。

| 事件 | 应做的状态转换 | 当前实验的证据 |
|---|---|---|
| 新申请 | 校验行情新鲜度、杀停开关、名义金额、含费资金和可卖量 | 过期行情和杀停两类新单被拦截 |
| 交易网关回执 | 待确认 → 工作中，然后接收成交或撤单流程 | 订单 A 申报 100 股 |
| 部分成交 | 成交数量与金额累加，资金和仓位同一事件结算 | 40 股 @5.01 |
| 撤单请求及中途成交 | pending cancel 期间继续接回报，满成则以成交终态为准 | 再成 20 股 @5.02，仍允许剩余部分撤回 |
| 撤单确认 | 终止剩余量，已成份额和费用保留 | 最终已成 60、已撤 40 |
| 重发 | 相同事件键和内容幂等，不同内容同键报错 | 重放 11 个独立事件，续跑新增 0 |

初始资金 2,000 元，成交金额 300.80 元，费用 0.30 元，期末现金 1,698.90 元，期末 60 股按 mid 5.06 估值为 303.60 元，权益为 2,002.50 元。权益多 2.50 元和 IS 成本 3.50 元可以同时成立。二者分别比较期初空仓与“在到达中间价买足 100 股”的假设基准。由此检查 TCA 的数量、比较基准和费用符号。[订单代码](../lab/execution.py) · [FIX 交易规范](https://archive.fixtrading.org/online-specification/business-area-trade/)

SQLite 日志写入前通过事务重放验证，每条写入都会扫描之前的事件，作为低规模教学实现具有 O(n²) 的总写入工作量。生产设计按账户或订单域维护带序号的投影，使用快照和增量更新，并在推进 checkpoint 前完成事务提交。原样重播需要持久化版本、随机种子和外部输入。当前夹具使用合成回报，未包含真实连接、完整 FIX 状态优先级、T+1 可卖量、交易日边界或券商交收接口。

## 运维屏和故障演练

| 故障表现 | 先检查 | 恢复证据 |
|---|---|---|
| 行情断流 / 延迟跳升 | 校验交易所序号、消费者 offset、交易时段、时间同步、上游与本地延迟 | 快照和增量达到同一水位，完整性及新鲜度回到阈值 |
| 订单超时、成交回报延迟 | 查看连接、在途订单、券商订单状态和成交查询，按订单键检索 | 在途状态分类明确，业务回报合并去重，资金仓位与独立来源一致 |
| 明细和实际仓位不符 | 成交 ID、买卖方向、数量单位、复权误用、费用、企业行动、结算日 | 提供账户/日期/标的差异明细，批准的调整可回放 |
| 日线晚到或修订 | 上游水位、文件哈希与架构版本。按可知时间保留旧快照 | 研究和仿真锁定明确快照；修订影响范围和回填版本可追踪 |
| 进程存活但状态未对齐 | readiness 标为不可用，核对部署清单、schema 和账本 checkpoint | 对账结束，回放版本通过，支持回退和恢复控制 |
| 大量告警 | 对比影响账户、品种和风险持续时间，区分首因与连锁告警 | 负责人、时间线、证据链接、恢复阈值、补测试及复盘都入日志 |

建议指标命名方向包括每通道序号 gap、交易所至本地 quote lag、回报延迟分位数、拒单原因计数、队列积压、PIT 覆盖率、对账差异和 replay hash。分位数要注明时间窗口、负载和时钟。账户、订单等高基数字段留在日志/trace。硬件优化时先用 perf/火焰图、分配器和上下文切换测量定位，再做 A/B。记录 p50、p99、p99.9、每秒事件和 CPU 负载，并以回放一致性作门槛。[OpenTelemetry 信号](https://opentelemetry.io/docs/concepts/signals/) · [Kubernetes probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)

## 智能化工程案例

给定“盘后仓位差 60 股”的问题，Agent 流程为读取有权限的对账快照 → 找对应订单 ID 与回报序号 → 取当时行情、部署版本和交易状态 → 返回含证据、推断和待核验项的诊断。形式字段包括 `incident_id`、`evidence_event_ids`、`observed`、`hypotheses`、`checks_to_run`。工具限定只读和账户范围。发单、恢复交易和账本调整的权限留在交易控制与人工审批链路。故障文本及附件作为证据读取，其内指令不进入工具权限判断。

离线评估集覆盖真实缺口、重复/冲突回报、只见局部证据、错误账户、修订导致误报、提示注入和缺失工具。衡量首因命中率、事件引用可核验率、覆盖率、误告警率、越权拦截率、响应耗时。先做 SQL + 规则和检索基线，再比较是否需要 LLM、SFT 或多模态。课程提供这一模块的系统设计和评估作业。

## SQL 和交付作业

把事件表投影为 `orders`、`fills`、`positions` 和 `cash_movements`（执行 ID 唯一），编写三条检查：

1. 每单累计成交量 ≤ 申报量，撤单确认后的重复回放不会再动账。
2. 每账户现金 = 昨日现金 ± 成交名义 − 费用 ± 独立入出金；分交易日、币种和结算可用口径。
3. 本地与外部的成交执行 ID 双向 anti-join。区分缺回报、重复、部分或在途；同 ID 的方向、数量、价格都要匹配。

将模拟器的 `MAX_QUOTE_AGE_MS` 设为更小并保留失败日志。随后加未确认回执、网络重连、进程崩溃后重发测试。提交时写清任务原始假设、失败输入、修复前后输出和当前限制。
